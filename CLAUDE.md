# CLAUDE.md — Moti

Guidance for Claude Code in this repo. Where this file and the global `~/.claude/CLAUDE.md`
disagree, the global plan-before-edit and commit-message rules still win.

Moti is a mobile-first **PWA**: React 19 + TypeScript + Vite, Tailwind v4 + **shadcn/ui
(`aria-vega`, React Aria)**, TanStack Query 5, zustand 5, react-hook-form + zod, and
**Supabase** as the only backend. The stack and folder law mirror
`Dcwd_Work/dcwd_apps-crm-customer2`; the Supabase layer mirrors `Ejie_Business/TARTAR`.

The app is built feature by feature from the Moti spec. Never build the whole app at once
unless explicitly instructed.

## Skills are mandatory — every prompt, no exceptions

**Every message starts by loading a skill.** Classify the request with the router below, call
the matching skill through the Skill tool, then work. A follow-up, a correction and a one-line
fix all count.

- `codebase-engineering` is the default. When nothing more specific fits, load that one.
- `token-efficiency` loads alongside it on any request that will read or search more than one file.
- Already loaded earlier in this conversation? Do not reload it — follow it.
- Reading and searching need no skill. **The first write always does.**

## Skill router

| Request looks like | Load |
|---|---|
| **Anything at all — the fallback when nothing below fits** | `codebase-engineering` |
| Any request that will read or search more than one file | `token-efficiency` (alongside) |
| Any code change, feature, bug fix, refactor | `codebase-engineering` |
| A new screen, table, modal, card, form, filter bar — anything the user sees | `ui-design-conventions` + `shadcn` |
| Adding or composing a shadcn component, `npx shadcn` CLI | `shadcn` (official skill) |
| Supabase: table, migration, RLS, RPC, storage, auth, service file | `supabase-backend` |
| Manifest, service worker, install/update, offline, safe areas, icons | `pwa-conventions` |
| "Where is X?", which file owns Y, impact of a change | `architecture-navigation` |
| Naming or placing a new file | `naming-conventions` |
| Splitting or extracting a component, hook, store, service | `componentization` |
| Relationships, dependencies, blast radius | `graphify-workflow` |

Load only what the request needs — but load at least one, every time.

The `shadcn` skill is the official one from `shadcn/ui`, pinned in `skills-lock.json`. If
`.claude/skills/shadcn/` is missing, restore it with `npx skills experimental_install`.

## Rules that hold everywhere

- **Plan before the first write** — numbered list of files and the change in each, then wait
  for approval (`codebase-engineering` § A).
- **Copy the nearest existing sibling**; never invent a second way to do something that already
  has one. Reuse → extend → new file (last resort).
- **Smallest correct change**, componentized and readable in the style already around it.
- **Infer the path before searching it** — the folder law below is strict enough to predict a
  path (`architecture-navigation`).
- **Supabase is touched only in `src/services/data/`**, through the one client in
  `src/utils/supabase.utils.ts`. Writes go through `runWrite` so the offline queue works.
- **Never run a migration or `supabase db push`** — write the SQL, hand the command over
  (`supabase-backend` § F).
- **Never run `graphify update .`** — the user runs it (`graphify-workflow`).
- **Every successful change ends with validation and a commit suggestion** (`codebase-engineering` § H).

yarn build           # tsc -b && vite build — the gate, must stay clean
yarn lint            # eslint — 0 errors, 0 warnings

This repo starts clean and must never acquire a type or lint error.

## Folder law — every file has exactly one home

```txt
src/
├── models/
│   ├── common/                 # shared contracts: route, modal, field, pagination, response, write
│   └── data/<domain>/          # <domain>.request.ts (zod schemas + inferred types), <domain>.response.ts
├── enums/                      # <domain>.enum.ts — string-literal unions + label/tone maps
├── keys/                       # query.keys.ts, modal.keys.ts, table.keys.ts, storage.keys.ts
├── services/data/              # <domain>.services.ts — Supabase calls, one default-exported object
├── hook/
│   ├── common/                 # modal, confirmation, pagination, search, filter, disclosure, network
│   ├── data/<domain>/          # <domain>.list.hook.ts (queries), <domain>.form.hook.ts (mutations + useForm)
│   ├── layout/                 # navigation.hook.ts
│   └── use-mobile.ts           # generated by shadcn — do not edit
├── store/
│   ├── common/                 # reset, modal, confirm, pagination, filter, layout, sync, network
│   └── data/<domain>/          # <domain>.store.ts
├── components/
│   ├── ui/                     # generated by shadcn — never hand-edited
│   ├── common/<kind>/          # app primitives; the ONLY layer that imports components/ui
│   └── <domain>/<kind>/        # feature code: cards/ modal/ panels/ tables/ forms/ wizard/
├── pages/<Domain>/             # <Domain>View.tsx — layout only
├── routes/                     # route.paths.ts, *.routes.ts, route.guard.tsx, index.ts
├── layouts/                    # AppLayout.tsx — authenticated shell
├── styles/
│   ├── common/                 # theme.css (tokens), typography.styles.ts, tone.styles.ts
│   ├── <kind>/                 # button/ cards/ modal/ table/ form/ layout/ view/ status/ filter/
│   └── <domain>/               # styles only one domain uses
├── utils/                      # *.utils.ts — supabase, write, env, error, format, cn, query, route
├── App.tsx                     # RouterProvider + the single ConfirmationModal
└── main.tsx
supabase/
└── migrations/                 # <YYYYMMDDHHMMSS>_<snake_name>.sql
public/                         # PWA icons, favicon, apple-touch-icon
```

Dependency direction — never skip a level:

```txt
pages → components → hook/data → services/data → utils/supabase.utils → Supabase
components → store, models, keys, styles, utils, hook/common
```

A component never imports Supabase; a page never calls a service; a service never imports React.

**Imports are relative.** The `@/` alias exists only because shadcn generates it: `@/components/ui/*`,
`@/hook/use-mobile` and `@/utils/cn.utils` — used inside `src/components/common/` and nowhere else.

## State

- **React Query** — every server row, its loading/error state, invalidation. Keys are constants
  in `keys/query.keys.ts`, composed with `scopedKey(...)`.
- **zustand** — everything else: modals (`useModal(key)`), confirmations (`useConfirm`),
  filters, search, pagination, wizard progress, view modes, the offline write queue.
- `useState` and `useReducer` are ESLint errors outside the generated layer.
- Stores are created with `create` from `store/common/reset.store.ts` so `resetAllStores()`
  clears them on sign-out. `persist` only with a key from `keys/storage.keys.ts`.
- Never cache server rows in a store.

## Forms

react-hook-form + zod. The zod schema lives in `models/data/<domain>/<domain>.request.ts` and its
`z.infer` type is the request model. `use<Thing>Form` in `<domain>.form.hook.ts` owns `useForm`
+ `zodResolver`, the mutation and the error text. Modal forms render through `EntityFormModal`
with an `IFieldConfig[]`. Read values with `useWatch`, never `form.watch()`.

## Code rules

- Functional components; **one default export at the bottom matching the filename**. Hooks,
  stores, models, keys, enums, utils, styles and routes use named exports. Services are one
  default-exported object.
- Props are a local `type IProps = { … }`. Domain models and shared contracts carry an `I` prefix;
  zod schemas are camelCase (`createTaskSchema`).
- TypeScript strict, no `any` — `unknown` plus narrowing. `import type` for type-only imports.
- Comments: a short single-line `//` for a non-obvious *why* only. No banners, no JSDoc essays,
  no commented-out code.
- No Tailwind class strings in JSX — named constants / `cva` variants in `src/styles/**/*.styles.ts`.
- No hex, px or rgba literals in components — add a token to `styles/common/theme.css`.
- Never delete existing files or user work without explicit confirmation.

## Completion checklist

1. `yarn build` and `yarn lint` — both clean (`codebase-engineering` § G has the ladder).
2. Report: files added, files changed, how to test, remaining notes.
3. Commit suggestion (`codebase-engineering` § H) — suggest only, never commit unless asked.
