# Token Efficiency

Cheap is not the same as sloppy. The goal is **the same correct answer from a third of the
reading**. Every rule here removes reading that was never going to change the outcome.

Load this with the working skill, not instead of it.

## 1. Size it before you read it

Never open a file to find out whether it is relevant. Ask a cheaper question first.

| Question | Command | Costs |
|---|---|---|
| Does this exist at all? | `find src -iname "*<feature>*"` | ~10 lines |
| Which files mention it? | `grep -rl "<Symbol>" src --include=*.ts --include=*.tsx` | one line per file |
| How big is the blast radius? | `grep -rc "<Symbol>" src --include=*.ts --include=*.tsx \| grep -v ":0"` | one line per file |
| How long is this file? | `wc -l <file>` | 1 line |
| Where in the file? | `grep -n "<Symbol>" <file>` | one line per hit |
| Which migration touched a table? | `grep -l "<table>" supabase/migrations/*.sql` | one line per file |

Only after those do you read, and then you read **the lines the line numbers pointed at**.

`grep -rn` across the repo is the expensive one. Reach for `-l` first and `-n` only once you know
which handful of files matter.

## 2. Read regions, not files

- Under ~150 lines: read it whole, fine.
- Over ~150 lines: `sed -n '40,90p' <file>`, driven by the `grep -n` you already ran. Several
  ranges in one command is still one call: `sed -n '1,30p;120,160p' <file>`.
- Need only a signature, a key or a type? `grep -n -A6 "<Symbol>" <file>`.
- Need only the contract? Read `models/data/<domain>/*.ts` and the service object, not the
  300-line component. The model is the answer to most "what does this carry" questions.
- Need the current schema of a table? `grep -n -A25 "create table.*<table>" supabase/migrations/*.sql`,
  then any later `alter table <table>` hits — not every migration file.

## 3. Always exclude the noise

Never read or search:

```
node_modules/  dist/  build/  dev-dist/  .history/  graphify-out/cache/
yarn.lock  *.tsbuildinfo  src/components/ui/  (generated by shadcn — read only to learn a prop)
```

Scope every search to `src/` (or `supabase/`) with `--include`. A root-level grep walks
`node_modules` and is the single most common way to waste a thousand tokens.

## 4. Batch independent calls

Two commands that do not depend on each other go in **one message**, as parallel tool calls. A
round trip costs more than the commands do. Typical opening move for a feature question:

```
find src -iname "*task*"                                    # where does it live
grep -rl "taskListKey" src --include=*.ts --include=*.tsx   # who touches it
```

## 5. Validate at the narrowest scope

| Change | Command |
|---|---|
| A single file, no new types | nothing |
| Types, models, services, several files | `npx tsc -b` |
| Before reporting a feature done | `yarn build`, then `yarn lint` |

Pipe to `head -30` when you expect many errors; the first few name the real cause. Never start
`yarn dev` / `yarn preview` — they block and carry no verdict.

## 6. Do not re-read what you already know

- A file you just edited: the edit either applied or errored. Do not read it back.
- A file read earlier in this conversation: it is still in context.
- A fact already established, a decision the user already made: do not re-derive or re-open it.

## 7. Write once, in the right shape

Rewriting costs more than the first write. Before creating a file, open **one** nearest sibling
(`codebase-engineering` § B) and copy its shape. One sibling, not four. Write a multi-line file
in a single Write rather than a Write followed by three Edits.

## 8. Answer at one altitude

- **One recommendation, not a survey.** Take the obvious default and say so in a line.
- **No preamble, no restating the request.**
- **Report the delta** — what changed, what it affects, what to run. Cite `path.ts:42` instead of
  pasting back code you just wrote.

## 9. When to spend anyway

Efficiency is never a reason to guess. Spend the tokens when:

- you are about to **write** to a file you have not read
- the change touches shared code (`components/common/`, `hook/common/`, `store/common/`,
  `utils/`, `styles/common/theme.css`) — run the blast-radius check (`architecture-navigation` § 5)
- the change touches the schema, RLS or an RPC
- a build failed and you do not yet understand why
- the request has two readings that lead to different work

A wrong answer delivered cheaply is the most expensive outcome available.
