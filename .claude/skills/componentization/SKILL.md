# Componentization

Split by **responsibility**, not by line count. Every extraction must pay for itself in reuse,
clarity, or testability.

## 1. Where each responsibility belongs

Ask in order, stop at the first "yes":

| Question | Home |
|---|---|
| Pure transform of values — no React, no data source? | `utils/<topic>.utils.ts` |
| A fixed set of values with labels / tones? | `enums/<domain>.enum.ts` |
| The shape of data going out or coming in? | `models/data/<domain>/<domain>.{request,response}.ts` |
| Talks to Supabase? | `services/data/<domain>.services.ts` |
| Client state read by more than one component, or that survives navigation? | `store/data/<domain>/<domain>.store.ts` |
| Query, mutation, form or orchestration for one screen? | `hook/data/<domain>/<domain>.<kind>.hook.ts` |
| Reusable across domains and purely visual? | `components/common/<kind>/` |
| Visual but meaningful to one domain only? | `components/<domain>/<kind>/` |
| Otherwise | the page |

If code sits in the wrong row, moving it is usually the right fix — not wrapping it.

## 2. The component tree

```
page (layout only)
 └── ContentView
      └── feature component (tables/ cards/ panels/ wizard/)   ← owns one hook call
           ├── cells/ or items                                  ← one cell's / row's look
           └── modal/                                           ← composes AppModal / EntityFormModal
```

- **One hook per feature component.** A component gets everything it renders from exactly one
  feature hook, which returns a flat object of primitives and handlers — never a nested bag.
- **Logic in the hook, markup in the component.** A component that computes and fetches is doing
  two jobs — move the query and handlers into `hook/data/<domain>/`.
- A block rendered the same way in two places becomes its own component (`cells/<Thing>Cell.tsx`).
- A component that renders three unrelated blocks becomes three components.
- A hook past ~150 lines is doing two jobs — split list from form, or read side from write side.

## 3. The shadcn boundary

- `components/ui/` is generated by `npx shadcn@latest add` and never hand-edited.
- `components/common/<kind>/` is the **only** layer that imports `components/ui/`. It wraps each
  primitive once (`AppButton`, `AppModal`, `DataTable`, `TextInput`) in Moti's vocabulary.
- Feature code composes `components/common/` only. If a feature needs a primitive that has no
  wrapper yet, add the wrapper to `common/` — do not import `ui/` from the feature.

## 4. Extract when

- The same markup or logic exists in **two or more** places (real duplication, not lookalike code).
  The moment a second domain needs it, it moves to `components/common/<kind>/` (or `hook/common/`,
  `utils/`) and both call it.
- A common component *almost* fits — **add a prop or variant** to it (`cva` variant in its
  `.styles.ts`) with the current behaviour as the default. Never fork a copy.
- Per-caller state is needed by a shared piece — generalize with a **keyed registry**, the way
  `useModal(key)` and `usePagination(key)` share one store with a key per caller.
- A service method mixes several Supabase calls that must succeed together — that belongs in a
  Postgres function called with `rpc` (`supabase-backend` § C).

## 5. Keep it inline when

- It is used once, is short, and reads fine where it is.
- The extraction would be a pass-through with no logic.
- The "shared" code only looks similar; the two callers will diverge.

No `XManager` + `XHandler` + `XFactory` layers, no wrapper components that only forward props, no
speculative generics, no barrel files.

## 6. Guardrails on load-bearing files

`App.tsx`, `main.tsx`, `layouts/AppLayout.tsx`, `routes/`, `utils/supabase.utils.ts`,
`store/common/sync.store.ts`, `store/common/reset.store.ts`, `styles/common/theme.css` and
`vite.config.ts` carry the whole app. Add to them rather than restructuring them, and confirm with
the user before any change that alters existing behaviour.

## 7. Splitting an existing large file

1. Identify the seams (distinct responsibilities), not arbitrary halves.
2. Keep the public surface identical unless the user asked for a change.
3. Move code, do not rewrite it, in the first commit.
4. `npx tsc -b`, then `yarn build` + `yarn lint`.
5. Tell the user what moved where.
